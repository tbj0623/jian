## 1. 出包

```bash
cd jian
npm run android    # debug APK，实测 BUILD SUCCESSFUL in 50s（304 tasks）
npm run release    # 正式签名 APK
```

产物：`android/app/build/outputs/apk/debug/app-debug.apk`、`apk/release/`、`bundle/release/app-release.aab`。

## 2. 起模拟器（无头）

```bash
"$LOCALAPPDATA/Android/Sdk/emulator/emulator.exe" -avd jian_test \
  -no-window -no-audio -no-boot-anim -no-snapshot-save -gpu auto &
adb wait-for-device
until [ "$(adb shell getprop sys.boot_completed | tr -d '\r')" = "1" ]; do sleep 2; done
```

实测冷启动 **65 秒**。现成脚本：`~/.qoder/mcp-out/emu-boot.ps1.sh <avd>`（启动 + 等待 + 截图一次搞定）。

> 用 agent-device 的 `boot` 冷启动会超时（它内部 90s 上限，Qoder 的 MCP 调用上限更短），
> 所以**启动模拟器用上面的命令行方式，其余步骤再用 agent-device**。

> **串口会漂，所以动手前先认领。** `adb devices` 里那台不一定是你起的：自己那台一退，
> 别人的 AVD 可能马上顶到同一个 `emulator-5554`（2026-09-23 就撞上了，当时 5554 是随拍会话的
> `suipai_r4`）。唯一的凭据是 `adb -s <serial> emu avd name` 回的那句 **`jian_test`**。
> 五套设备脚本现在都先走这一步（`test/device_avd.py` 的 `require_avd()`：认不出来就退出，
> 并把该怎么做写在脸上），**手敲的每一条 adb 也必须带 `-s`**——打到别人的机器上不是量错，是动了别人的东西。

## 4. 业务层验证：走 CDP，不要走无障碍树（本项目关键）

Capacitor 的界面全在 WebView 里，`uiautomator` 只能看到一个 `WebView` 节点，
拿它点按钮等于闭眼操作。正确通道是 Chrome DevTools Protocol：

```bash
PID=$(adb shell pidof com.jian.app)
adb forward tcp:9222 localabstract:webview_devtools_remote_$PID
curl -s http://127.0.0.1:9222/json      # 能看到 title「笺」+ webSocketDebuggerUrl
```

现成工具（零依赖，Node ≥ 21）：`C:\Users\11930\.qoder\mcp-out\cap-cdp.mjs`

```bash
node ~/.qoder/mcp-out/cap-cdp.mjs url
node ~/.qoder/mcp-out/cap-cdp.mjs eval "document.body.innerText.slice(0,200)"
node ~/.qoder/mcp-out/cap-cdp.mjs tap "#nav-yan"                       # 真 touch 事件
node ~/.qoder/mcp-out/cap-cdp.mjs type "#yanText" "小红：明天下午三点把合同发给法务"
node ~/.qoder/mcp-out/cap-cdp.mjs tap "#runYan" shot y.png
```

命令：`url | eval | text | shot | tap | tapxy | type | keys`，可串联。
`type` 用原生 setter + `input` 事件，**中文直接进**；`tap` 发的是真实触摸事件，能触发监听器。

**整套回归已经脚本化**：`python test/device_verify.py`（装 debug 包 → 起 App → 在真 WebView 里
跑一遍改名/改品类/撤销/焦点找回/忌口折叠 + 真触摸 + 无横向溢出 + localStorage 落盘，22 项，
并把三屏截图写到 `.impeccable/review/device-*.png`）。它要一台在线的模拟器，所以**不进 `npm run check`**。

三个坑：

- **`eval` 只求值表达式，不会替你调用函数**：传 `() => {...}` 只会拿到 `{}`，得写成 IIFE 并带上结尾的
  `()`（`(() => {...})()`）。异步的也行——它带 `awaitPromise`。
- **release 包默认没有 CDP**。`CapConfig` 里 `webContentsDebuggingEnabled` 缺省跟随 `isDebug`；
  要在正式包上验，得在 `capacitor.config.json` 显式加 `"android": { "webContentsDebuggingEnabled": true }`
  （上架包不建议开）。
- **Playwright 的 `connectOverCDP` 连不上 WebView**，会报
  `Protocol error (Browser.setDownloadBehavior): Browser context management is not supported`。
  浏览器里调 H5 用 Playwright，设备上用 cap-cdp，两套别混。

## 5. 原生层验证：agent-device

系统照片选择器、分享面板、权限弹窗、触感这些在 DOM 里看不见，用 agent-device 驱动：

```bash
agent-device open com.jian.app --foreground          # 返回带 @eNN 的快照
agent-device snapshot -i                             # 只列可交互节点
agent-device click @e12 --settle                     # --settle 返回 UI diff，这才是验证
agent-device screenshot
agent-device logs
agent-device doctor
```

- CLI 与 Qoder 的 MCP 会话**不是同一个命名空间**：MCP 建的会话叫 `default`，CLI 默认用
  `cwd_<hash>_default`。CLI 报 `SESSION_NOT_FOUND` 时加 `--session default`。
- MCP 里 `devices / open / snapshot / screenshot / press(坐标)` 实测可用；
  **`click` / `fill` 走 MCP 在 0.21.6 有缺陷**（响应缺 `targetKind` 等字段而报错，且动作不执行），
  要 ref 型交互请用 CLI。
- 原生 `input text` 只支持 ASCII，中文靠它自带的 test IME（`fill` / `type`），别用 `adb shell input text`。

## 6. 已知设备限制

- AOSP `default` 镜像**没有震动器**（`pm list features` 无 vibrator），落章触感只能验到桥接调用返回成功。
  需要真触感反馈就上 `google_apis` 镜像或真机。
- 相册类广播 `MEDIA_SCANNER_SCAN_FILE` 在 API 35 已无接收者；要给设备塞测试图片：
  `adb push x.png /sdcard/DCIM/Camera/` 然后
  `adb shell content call --uri content://media/external/images/media --method scan_file --arg /sdcard/DCIM/Camera/x.png`。
- 内存 14 GB，**同时只跑一个模拟器**。
- **`<input type="date">` 起的是原生日历，但它不换窗口**（2026-09-21 实测，API 35 模拟器 + 随包 WebView）：
  点下去之后 `dumpsys window` 的 `mCurrentFocus` **还是** `com.jian.app/MainActivity`，
  所以「看当前窗口有没有变」判不出它开没开；要判就得 `uiautomator dump`（树里出现
  `android.widget.DatePicker`）或者截图。CDP 那一侧 `document.activeElement` 仍是 `INPUT/date`，
  页面还活着，按返回键收掉之后日期框仍在 DOM 里。
  两个推论：① 设备侧要验这一格，用 uiautomator/截图，不要用窗口焦点；
  ② 日历格在 dump 里**没有 `text` 属性**（按「21」这种文字去找节点是找不到的），
  要么按坐标点，要么读 `content-desc`。
- **原生弹层的强调色默认是 Material 青绿**，跟这张纸不是一回事（同一个截图前后对比过：
  日期选择器整个是青的）。修法是给运行时主题 `AppTheme.NoActionBar` 补
  `colorAccent` / `colorPrimary` / `android:colorControlActivated` → `@color/seal_red`（印章红，
  白字压上去 5.24:1）。这条颜色同时写在 `styles.css` 的 `--seal` 与 `res/values/colors.xml` 里，
  由 `npm run test:pkg` 的「墨色对账」对着查（它还顺手扫 res/values 里注释写了两个连字符的
  ——那是 XML 非法记号，而 aapt2 只回一句 not well-formed，要等 90 秒构建才看得见）。

- **这台 `jian_test`（API 35）量不出安全区：`--sab` 是 0px**（2026-09-23 实测）。
  视口 818 高，而 1080×2400 / DPR 2.625 折算应是 914——差的那 ~96px 是系统栏，
  被排在 WebView **之外**，也就是说这台机器上 WebView 没有铺到屏幕边，`env(safe-area-inset-bottom)` 恒为 0。
  两个后果：① 第 53 轮那处「提示条要让开底栏」的修复**在这台设备上无法复现那一档**，
  只能靠把 `--sab` 覆写成 48px 的模拟验证（`test/e2e.playwright.py` §55）；
  ② targetSdk 36 在 Android 15/16 上会被强制 edge-to-edge，那时 inset 才会真的非零——
  **这一条属于「待确认」，要一台真手机或一台配成手势条的 AVD 才能盖章**。

  > **⚠ API 35 复核（这一条是 0.6.0 之后补的，与上面那段并列读，不要只看上面）。**
  > 上面那段「安全区恒为 0」是 **0.6.0 之前**（targetSdk 更低、系统栏排在 App 之外）留下的实测记录。
  > 现在这个包是 **targetSdk 36**，在 Android 15 上被强制 edge-to-edge：系统栏那一层由应用自己画，
  > 也就是说 `env(safe-area-inset-*)` **不应该**再恒为 0。
  > **本轮以重新量到的值为准**：如果这一轮在 API 35 上量到的 inset 不是 0，
  > 那么上面这条结论、以及连带的「`--sab` 覆写成 48px 才算能验」都要改写成「实测非零，已覆盖」。
  > 量法见下面那条 gestural overlay。**在没重新量到之前，不要引用「恒为 0」当事实。**

- **`tap_at` 这类「按元素中心落点」的探针必须先把目标滚到视口中线**（同一个坑，2026-09-23）：
  `device_verify` 点「笺册第一行」报 `MISS @206,896 -> 什么都没有`，而 896 在 818 高的视口外面。
  原脚本只等滚动停稳、从不滚动目标；第 50 轮把「导出/导入备份」那一格搬到笺册**上面**之后
  这一行就掉到折叠线以下了。修法 `scrollIntoView({ block: 'center' })`——
  只写 `scrollIntoView()` 是「保证露出一个角」，中心仍在屏外，等于没修。
  顺带：**落点没命中之后紧跟着的那段 JS 不许假定上一次点击成功了**
  （`window.__copied.at(-1)[0]` 在空数组上抛 `Cannot read properties of undefined`，
  把一次「该报红的 MISS」变成了「套件崩了」）。

- **要把「非零安全区」真的量出来，办法找到了（但本机内存不够，还没跑通）**：
  AOSP 模拟器上导航栏模式是一组 RRO，`cmd overlay list` 能看见
  `com.android.internal.systemui.navbar.{threebutton,twobutton,transparent,gestural}`。
  默认是 three-button（系统栏**排在 App 之外**，所以 `env(safe-area-inset-bottom)` 恒为 0）；
  换成 **gestural** 之后手势条是覆盖在内容上的，那一档 inset 才会非零：
  ```bash
  adb -s <串口> shell cmd overlay enable com.android.internal.systemui.navbar.gestural
  adb -s <串口> shell cmd overlay enable com.android.internal.systemui.navbar.transparent
  ```
  2026-09-23 实测：命令找到了、`dumpsys window` 里也确实有 `Taskbar` 作导航栏，
  但**当时本机只剩 0.38GB 空闲**（另一台会话的 `suipai_r4` 同时占着 5554，两台模拟器一起吃内存），
  没有继续跑——内存吃紧时量出来的一切都不算数（ANR 会把每一次点击吞掉）。
  留这条给下次：**先确认 `adb devices` 上只有你自己那一台、空闲 ≥5GB，再开**。
  另注意串口会漂：那次自己的 `jian_test` 起在了 `emulator-5556`，`5554` 是别人的——
  所以每条命令都带 `-s`，动手前先 `adb -s <串口> emu avd name` 认领。
- **`--sat`（状态栏那一档）目前也只有模拟验证**：`.screen` 的上内边距写成
  `calc(30px + var(--sat))`，`.seal-mark` 又是 `top: calc(var(--sat) - 12px)`，
  这两处在非零 inset 下会不会把标题挤出纸面，`test/e2e.playwright.py` §55 用覆写 `--sat` 的量法覆盖
  （真机上 Android 15/16 强制 edge-to-edge 之后才会真的非零）。

## 6.5 0.6.0 原生能力自验：通知 / 分享接收 / 深色 / 快捷方式 / 返回键

这一节是 0.6.0 新加的五个原生能力，每一格都写了「怎么量」与「量到什么算对」。
共同前提：调试包已装、`ANDROID_SERIAL` 指向自己那台（`adb -s <串口> emu avd name` 要回 `jian_test`，
串口会漂，见第 2 节）。

### 6.5.1 本地通知（渠道 + 权限 + 真弹一条）

渠道是**原生侧**建的（`MainActivity.ensureRemindChannel()`，`jian-remind`，IMPORTANCE_DEFAULT），
不是网页调的：开机恢复提醒可能比插件初始化更早，渠道晚建一步，安卓 8+ 会静默丢通知。

```bash
# 渠道真的存在，importance=3（DEFAULT）、锁屏不显示正文
#
# ⚠ API 35 实测：渠道是**一整行内联**的，不是 13/14 那种分行块：
#   NotificationChannel{mId='jian-remind', mName=到点提醒, mDescription=…, mImportance=3,
#                       mBypassDnd=false, …, mLockscreenVisibility=2, …}
#   后面还跟着 mSound / mVibrationEffect / mUserLockedFields / mDemoted… ，所以 `-A3`
#   抓到的三行里**不一定**有 mImportance——它可能在同一个物理行的第 300 个字符之后。
#   正确读法是按 `NotificationChannel{` 切开、在那一块里找 mId= / mImportance= /
#   mLockscreenVisibility=（脚本见 test/device_accept.py 的 channel_block()）。
adb -s $S shell dumpsys notification --noredact | grep -o "NotificationChannel{[^}]*jian-remind[^}]*}"
# 期望在同一行里同时看到：  mId='jian-remind'  mName=到点提醒  mImportance=3  mLockscreenVisibility=2
#                           （2 = VISIBILITY_PRIVATE：「不摊在锁屏上」是隐私政策之外的一条自律）

# 权限声明对不对（release 包这份才是用户装到的）
$AAPT dump badging app-release.apk | grep uses-permission
# 期望六条：INTERNET / VIBRATE / RECEIVE_BOOT_COMPLETED / WAKE_LOCK /
#           POST_NOTIFICATIONS / com.jian.app.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION
# 关键：**没有** SCHEDULE_EXACT_ALARM（用 tools:node="remove" 在合并时摘掉了，
#       它在 Play 属于受限权限，而笺只承诺「大约这个点」）

# 排一条 1 分钟后的提醒，真等它弹出来（走 UI：言笺 → 某条右侧铃铛）
adb -s $S shell dumpsys alarm | grep -A2 'com.jian.app'
# 期望：有一条 RTC 类型的 alarm，且不是 setExact*（非精确 = 我们的口径）
```

**`POST_NOTIFICATIONS` 的运行时权限框在哪一步弹（API 35 实测）。**
不是「进言笺时」，也不是 `checkPermissions()` 时——`checkPermissions()` 只读状态，
既不查也不弹。plugins 的实现（`@capacitor/local-notifications` 8.3.1，
`LocalNotificationsPlugin.kt:101`）：

```kotlin
private fun shouldRequestNotificationPermission(): Boolean =
    Build.VERSION.SDK_INT >= TIRAMISU && getPermissionState(LOCAL_NOTIFICATIONS) != PermissionState.GRANTED
```

这个判断只在 `schedule()` / `update()` 里被调用。所以**用户第一次按「定下来」的那一刻**，
系统权限框先挡一下，点允许之后那条通知才真的排上（`scheduleAfterPermission` 回调）。

13/14 与 15 在这条上行为一致，差别只在 15 的框文案与「拒绝两次之后不再弹」更严格。
**对自动化脚本的影响**：必须在排之前 `pm grant`，否则会卡在一个系统框上，
看起来像「通知没弹」——这是**测试环境**问题，不是产品缺陷。
`test/device_accept.py:556` 已经显式 `pm grant com.jian.app android.permission.POST_NOTIFICATIONS` 并注明原因。

### 6.5.2 系统分享接收（ACTION_SEND，冷启动 + 热启动两条都要走）

```bash
# 冷启动那条（先把 App 从最近任务里划掉）
adb -s $S shell am force-stop com.jian.app
adb -s $S shell am start -a android.intent.action.SEND -t text/plain \
  --es android.intent.extra.TEXT '明天记得把材料发我' -n com.jian.app/.MainActivity
# 期望：落在「言笺」，输入框里已经有那句话，底部一句「已贴进言笺。里面有时间，捞出来会带上」

# 热启动那条（App 还在后台，这是最容易漏的一条：只写 onCreate 的话这里会静默丢内容）
adb -s $S shell input keyevent KEYCODE_HOME
adb -s $S shell am start -a android.intent.action.SEND -t text/plain \
  --es android.intent.extra.TEXT '药快没了帮我买一盒' -n com.jian.app/.MainActivity
# 期望：切回前台、追加到输入框末尾（不是覆盖），并且不重新走一遍开机
```

为什么热启动这条单列：`singleTask` 下第二次分享走的是 `onNewIntent`，
不覆盖它的话表现是「界面一切正常，那段话没了」——只在「App 已经开着」时复现，最难报。
长度上限 4000 在原生侧先截断（与 `share.js` 同一个数），因为几十万字的分享拼进
`evaluateJavascript` 会直接把 WebView 卡死。

### 6.5.3 深色主题：夜纸 #1b1917，原生与 CSS 逐字相同

```bash
# 切系统夜间模式（API 35 上这条照样成立，回显是 "Night mode: yes" / "Night mode: no"）
adb -s $S shell cmd uimode night yes
# 判「真的切过去了没有」只能读上面这一句，
# **不要**读 settings get secure ui_night_mode —— 见下面那条 ⚠
adb -s $S shell am force-stop com.jian.app && adb -s $S shell am start -n com.jian.app/.MainActivity
adb -s $S exec-out screencap -p > night.png     # 取整屏最多的那个颜色当纸色
adb -s $S shell cmd uimode night no
```

**⚠ API 35 实测：「系统确实切到了夜间」的判据不是 secure 值。**
`settings get secure ui_night_mode` 回答的是「用户有没有手动覆盖过」，不是「此刻是不是夜间」：

- **13/14 上**：只要有人在设置里动过一次，它就是 `"2"`（`UI_NIGHT_MODE_YES`）。
- **API 35 实测**：**没人动过时它是 `null`**（本机实测就是 `null`），
  而此时 `cmd uimode night` 明明回 `Night mode: no` / `yes`。

所以判据改成问 UiModeManager 本人：`cmd uimode night`（不带参数是**读**），
输出里取 `Night mode: yes|no|auto`。已改在 `test/device_deeplink.py` §5（第 269-275 行那段注释写着原因）。

期望：夜里主色 ≈ `#1b1917`（`styles-v06.css` 里 `:root[data-theme="dark"]` 的 `--paper`），
白天 ≈ `#f4efe6`；两者与 CSS 的差都 ≤ 12（逐通道）。这一节现在由
`test/device_deeplink.py` §5 自动跑：它**从 CSS 里读出两个色值再和截图比**，
而不是在测试里写死——CSS 改了纸色没跟上原生 res，那条会红。

**⚠ API 35 实测：系统条的「底色」已经不由 res 决定了。**
只要 `targetSdk ≥ 35`（本包是 36），应用被强制 edge-to-edge，
`Window.setStatusBarColor()` / `setNavigationBarColor()` **不再有任何视觉效果**——
系统条下面露出来的是应用自己画的那一层（也就是网页这张纸）。

| 管什么 | 15+ 上还生效吗 | 谁管 |
|---|---|---|
| 系统条**图标深浅** | **仍然生效** | `windowLightStatusBar` / `windowLightNavigationBar`（`values-night/styles.xml`），运行时还有 `ui.js` 的 `paintNativeChrome()` 与 `MainActivity.syncSystemBarIcons()` 兜底 |
| 系统条**底色** | **失效** | 由 `body` 背景铺到条下面决定 |

所以指南原来那句「夜里系统条会变成夜纸色，靠的是 res 那两条」是 15 之前的说法。
现在正确的判据是：**截图里系统条上不应该出现第二种底色**——它必须是这张纸自己的颜色
（夜里 ≈ `#1b1917`、白天 ≈ `#f4efe6`）。`ui.js:173-175` 的注释记了这一条。
`res/values-night/` 仍然要留，它管的是**原生自己画的**那几帧：启动图底色、系统弹层强调色、
以及上面那一行图标深浅。

### 6.5.4 快捷方式：五枚，逐枚点名

**⚠ API 35 实测：`dumpsys shortcut` 的输出形状变了，`grep -A2` 抓不到要判的东西。**

- 整份 dump 把所有包**混排**，还多了 `PackageInfo:` / `IsShadow: false (installed)` /
  `Launcher: …` 这些区段；本机整份一万多行、要 8~12 秒。
- `grep -A2` 基本只能抓到 `ShortcutInfo {id=…, flags=0x1a4 [ImManIc-rStr]` 和
  `packageName=com.jian.app` 两行——**抓不到 `shortLabel` / `intents`**，
  而这两样才是「五枚挂上了没有」「地址对不对」的判据。
- 标签形状是 `shortLabel=过一件衣, resId=2131…[shortcut_yi_short]`：中文在，
  但后面**一定**跟着 `resId=`。所以「短标签不是 `res/` 开头」这种断言在新格式里恒为真，等于量空气。

```bash
# 取值用 cmd shortcut get-shortcuts：只出这一个包，格式与 dumpsys 内那段逐字相同，快一个量级
adb -s $S shell cmd shortcut get-shortcuts com.jian.app
# dumpsys shortcut 留作兜底（个别 ROM 上 get-shortcuts 不打印）
# 期望五枚，逐枚对得上的三件事：shortcutId / shortLabel（**值里有汉字**）/ intent 里的地址
#   yi    jian://screen/yi
#   wei   jian://screen/wei
#   yan   jian://screen/yan
#   today jian://screen/today
#   note  jian://screen/yan?new=1        ← 注意 id 与地址不是同名：note 落到言笺
adb -s $S shell am start -a android.intent.action.VIEW -d 'jian://screen/today'
# 期望：直接落在「今日」那一屏（不是首页再点进去）
```

判据从「前缀不是 `res/`」改成「**值里有汉字**」（`[\u4e00-\u9fff]`）。
已改在 `test/device_deeplink.py` §4（第 160-185 行）。`npm run test:pkg` 的
`checkShortcuts()` 在构建侧对着查三头：`shortcuts.xml` 的地址、清单里的注册、
`ui.js` 的 `screenOf()` 认不认得那个屏名。

五枚是 `ShortcutManager` 的上限，再加就得先降级一枚。`note` 那个 `?new=1` 不是装饰：
以后要把它演进成「清空输入框再来一笔」时，改行为不用重新注册快捷方式。

### 6.5.5 返回键：十一个子页逐个按

`enableOnBackInvokedCallback="true"` 已经写了，链路是 `ui.js` 的 `SUB_OF`/`backStack`
→ `app.js` 的 `registerNativeBack` → App 插件的 `backButton`。

```bash
# 以「单品详情」为例：衣笺 → 柜子 → 某件「档案」，然后
adb -s $S shell input keyevent KEYCODE_BACK
# 期望：回到衣笺（不是退出 App）；在首页再按一次才是退到后台
```

**`SUB_OF` 现在有 11 条**（`ui.js:260-272`，v0.6.0 时是 9 条，后来补了 `pu` 与 `year`）：

| 子页 | 从哪张纸翻过来 | 子页 | 从哪张纸翻过来 |
|---|---|---|---|
| `yi-report` | `yi` | `yan-remind` | `yan` |
| `yi-item` | `yi` | `settings` | `me` |
| `yi-outfit` | `yi` | `search` | `me` |
| `wei-dish` | `wei` | `pu`（笺谱） | `today` |
| `wei-week` | `wei` | `badges`（成就） | `pu` |
| | | `year`（年度） | `pu` |

逐个走一遍，判据只有一条：**按返回先回上一屏，回到栈底那次才退后台**。
返回栈为空时 `goBack()` 返回 false，`registerNativeBack` 才调 `minimizeApp()`——
不这么写就会「按一下直接退出」。`badges` 与 `year` 是**二级**子页（从 `pu` 翻过去），
所以它们回来是回笺谱，不是回今日——这一条最容易写错。

### 6.5.6 这一节的边界：哪些**必须**真机/模拟器才验得到

| 能力 | 构建/静态能验 | 只能设备验 |
| --- | --- | --- |
| 通知渠道 | `dumpsys notification` 静态可读（按 `NotificationChannel{` 切块，不要 `-A3`） | 真弹一条、权限框、Doze 延迟 |
| 分享接收 | 清单里 filter 在、Java 编过 | 冷启动/热启动两条真链路 |
| 深色 | 两个 colors.xml 与 CSS 对账 | 系统条图标在真夜纸上的可读性、系统条底下是不是同一张纸 |
| 快捷方式 | 五枚 id/地址/标签对账（`cmd shortcut get-shortcuts`） | 系统注册表里真的挂上了 |
| 返回键 | `SUB_OF` 覆盖 11 页 | 按下去真的回上一屏 |

## 6.6 API 35 / Android 15 与「13/14 口径」的五处差异（速查）

这一节的完整核对过程在 `test/DEVICE-API35-NOTES.md`，那里每条都写了「13/14 是什么、
15 实测是什么、判据该怎么改」。这里只留结论，**动手之前先看这一张表**：

| # | 你在 13/14 上习惯的判据 | API 35 实测 | 改成什么 |
|---|---|---|---|
| 1 | `settings get secure ui_night_mode` 是 `2` | 没人手动设过时是 **`null`**；它回答的是「有没有被覆盖过」，不是「此刻是不是夜间」 | 读 `cmd uimode night` 的 `Night mode: yes\|no\|auto`（§6.5.3） |
| 2 | `dumpsys shortcut \| grep -A2` 能抓到 label/intents | 混排 + 新增区段，`-A2` **抓不到** `shortLabel` / `intents`；标签里一定跟着 `resId=` | 用 `cmd shortcut get-shortcuts <pkg>`；判据从「前缀不是 `res/`」改成「值里有汉字」（§6.5.4） |
| 3 | 系统条底色靠 `res/values-night` 的 `statusBarColor` / `navigationBarColor` | `targetSdk ≥ 35` 强制 edge-to-edge，**这两个 setter 没有视觉效果** | 「图标深浅」仍由 `windowLightStatusBar` 管（这条 15 上仍生效）；「底色」由网页这张纸决定，判据是截图里条上不出现第二种底色（§6.5.3） |
| 4 | `checkPermissions()` 会查（或弹）通知权限 | 只在 `schedule()` / `update()` 里查（`LocalNotificationsPlugin.kt:101`） | 权限框在**第一次 schedule 时**弹；自动化脚本排之前必须 `pm grant`（§6.5.1） |
| 5 | `env(safe-area-inset-*)` 恒为 0 | targetSdk 36 + Android 15 强制 edge-to-edge，**大概率已经不成立** | **待重新量**，以截图与量到的值为准；没量到之前不要引用「恒为 0」当事实（§6 里那条并列的 ⚠ 段） |

另外两条**不需要改**的，记在这里省得下次又核一遍：

- **`dumpsys gfxinfo` 的字段**：API 35 上 `Total frames rendered:` 与 `Janky frames` 都在，
  但多了一行 `Janky frames (legacy):`。`test/device_perf.py` 现在取**第一行**（新口径），是对的；
  哪天有人改成取最后一行，会拿到 legacy 那个数——本机桌面上实测 81.31% vs 77.57%，差 4 个百分点。
- **WebView 版本仍是 124.0.6367.219**，`test/device_perf.py` 里那八条预算的基线仍然可比。
  一旦镜像升到 WebView 13x，那些基线（注释里的「14 / 143」「2.4 / 19」）就要重测一遍。

还有一条边界，贴证据时容易忘：`dumpsys notification --noredact` 的正文
**只在 userdebug / eng 上才有**（本机 AVD 是 `userdebug/dev-keys`，能拿到）；
**真机上 `adb shell dumpsys notification` 不给 `android.text`**。
报告里贴这段证据时要写明「这是模拟器特权输出」，别让人以为零售机能这样读到用户通知内容。


## 7. iOS：暂缓，但先把事实钉住

- 本机（Windows）不能跑模拟器、签名、`.xcframework` 链接、XCTest、上传 App Store Connect——这些必须有 macOS。
- 但 `docs/双端打包指南.md` 里「Windows 上无法生成 iOS 工程」这句是**错的**：
  `npx cap add ios` 只是解模板，不检查平台；`cap sync ios` 只是提示「Skipping pod install because CocoaPods is not installed」。
  也就是说：**可以在 Windows 上生成并提交 `ios/App`，构建交给 macOS 环境**（GitHub Actions 的 macOS runner，公开仓库免费）。
- 等有了 Mac 或决定走云构建时，按那份指南第 2 节继续即可。
